# Java Interview Prep

A hand-edited, build-less **static study site** for Java / Spring Boot interview
preparation, served from Vercel. It combines a searchable Java/Spring question
bank, a curated set of LeetCode problems with idiomatic Java solutions, and a
floating AI chat assistant backed by a single serverless function.

- **Live site:** https://java-interview-prep-blush.vercel.app
- **Repo:** https://github.com/SYLin117/java-interview-prep
- **Stack:** plain HTML + CSS + vanilla JS (no framework, no bundler, no build
  step) and one Vercel **Edge** function.

> There is **no database**. All content ships as plain JavaScript data files
> loaded directly by the browser. The ["Data model"](#data-model) section below
> documents the shape of each of those files — that *is* the "database" of this
> project.

## How it works at a glance

- **Static HTML/CSS/JS.** Open `index.html` and everything is there — no
  compilation.
- **Content is data, not markup.** Questions, LeetCode problems, descriptions
  and algorithm notes live in separate `*.js` files. Adding content never
  touches the HTML.
- **Two views, one page.** Header buttons toggle between a **Topics** view (the
  Java/Spring question bank) and a **LeetCode** view, using the `[hidden]`
  attribute so only one is in the layout at a time.
- **Single inline script** in `index.html` orchestrates everything: render,
  view toggle, search, side-nav, the chat widget, and resizing.
- **One serverless function** (`api/chat.js`) proxies the chat to Groq with
  rate-limiting and SSE normalization.
- **Manual deploys** to Vercel (`vercel deploy --prod --yes`).

### What each file does

| File | Role |
|---|---|
| `index.html` | The entire UI. Contains the markup skeleton, all CSS, and one inline `<script>` (~600 lines) that renders both views, wires the search box, side-nav, view toggle, URL-hash routing, and the chat widget. |
| `content.js` | The interview question bank — `const topics = [...]` (12 topics) plus `const extras = {...}` (one extra topic for MQ/Redis/Docker/K8s). ~262 questions total. |
| `leetcode.js` | `const leetcode = [...]` — 110 popular LeetCode problems, pre-sorted into 15 buckets, each with an approach hint, complexity, and a full Java solution. |
| `descriptions.js` | `const leetcodeDescriptions = {...}` — short paraphrased problem statements keyed by the LeetCode `num`. Shown in a problem's expanded panel. |
| `algorithms.js` | `const namedAlgorithms = {...}` (explanations + worked traces for named algorithms like Kadane's, Dijkstra's) and `const problemAlgorithms = {...}` (maps a LeetCode `num` → the algorithm keys it uses). |
| `user-overrides.js` | `const leetcodeUserOverrides = {...}` — personal edits to LeetCode solutions that override the canonical `code` from `leetcode.js`. Generated by the "Export edits" button on the live site. |
| `api/chat.js` | Vercel Edge function. Proxies the chat assistant to Groq (Llama 3.3 70B), rate-limits per IP, and normalizes the upstream SSE stream into a provider-agnostic `{ text: "chunk" }` event stream. |

All five browser-side JS files are **classic (non-module) scripts**. They are
loaded in this order in `index.html` *before* the inline script:

```html
<script src="content.js"></script>
<script src="leetcode.js"></script>
<script src="descriptions.js"></script>
<script src="algorithms.js"></script>
<script src="user-overrides.js"></script>
```

Because they are classic scripts, every top-level `const` (`topics`, `extras`,
`leetcode`, `leetcodeDescriptions`, `namedAlgorithms`, `problemAlgorithms`,
`leetcodeUserOverrides`) lands in the shared global lexical scope, so the inline
render script reads them directly. **Do not convert these to
`type="module"`** — module scope is private and would break the cross-script
references.

## Runtime architecture

### Page lifecycle

1. The `<head>` loads Google Fonts (JetBrains Mono), the highlight.js CSS theme
   (atom-one-dark), and highlight.js itself (`defer`).
2. The `<body>` parses: a sticky header (brand, view toggle, search, stats),
   `<div id="topics-view">` with placeholder containers, a hidden
   `<div id="leetcode-view">`, a footer, and the chat-widget skeleton.
3. The five data scripts run and define their globals.
4. The **inline script** runs synchronously and:
   - merges `topics + extras` into `allTopics`;
   - builds the topic cards, side-nav links, and all topic sections;
   - builds all LeetCode rows (grouped by `bucket`);
   - wires click-to-expand, the `IntersectionObserver` side-nav highlighting,
     the view toggle + URL-hash routing, the view-aware search, and the chat
     widget.
5. Deferred highlight.js finishes and colorizes any already-rendered code.

### Two views

A segmented control in the header switches between **Topics** and **LeetCode**
via the HTML `hidden` attribute. URL-hash routing keeps them linkable:

| URL hash | View |
|---|---|
| (none) or `#core-java`, `#collections`, … | Topics |
| `#leetcode` or `#lc` | LeetCode |

### Topics view

For each topic in `allTopics`, the script renders a `<section>` with one
expandable row per question. Questions are **sorted by difficulty**
(easy → medium → hard) at render time. Clicking a row toggles `.expanded`;
clicks *inside* an answer are ignored so users can select/copy text without
collapsing the row. Topic answers contain pre-escaped HTML and are rendered via
`innerHTML`.

### LeetCode view

Iterates `leetcode[]`, rendering one row per problem and inserting a styled
section header whenever the `bucket` changes (this is why the array must stay
pre-sorted by bucket). Expanding a row reveals the paraphrased description
(from `descriptions.js`), any named-algorithm notes (from `algorithms.js`), the
approach, complexity, and the Java solution. Unlike topic answers, LeetCode
`code` is stored as raw Java and HTML-escaped at render time, and highlight.js
runs **lazily** the first time a row is expanded.

### Chat widget

A floating 💬 button opens a panel. Before calling the LLM, the widget tries a
**local token-overlap match** against the question bank; if ≥60% of significant
query tokens (and ≥2 absolute) match a known question, it answers locally with
zero LLM cost. Otherwise it POSTs the recent conversation to `/api/chat` and
streams the response.

For a much deeper treatment of layout, responsive breakpoints, search scoping,
and the resize logic, see [`ARCHITECTURE.md`](./ARCHITECTURE.md).

## Data model

There is no SQL/NoSQL database — the "schema" is the shape of the JS data
objects below. Each is a plain `const` in its file.

### `content.js` — question bank

**`topics`** is an array of topic objects (12 of them). Their `id`s, in order:
`core-java`, `collections`, `multithreading`, `jvm`, `spring-core`,
`spring-boot`, `spring-mvc`, `data-jpa`, `security`, `spring-multithreading`,
`microservices`, `vibe-coding`.

```js
// Topic
{
  id:   'core-java',                       // unique slug → used as the section anchor (#core-java)
  name: 'Core Java & OOP',                 // display title
  desc: 'Fundamentals, OOP principles…',   // one-line subtitle
  questions: [ /* Question objects */ ]
}

// Question
{
  d: 'easy' | 'medium' | 'hard',           // difficulty — drives sort order + the pill color
  q: 'What is the difference between == and .equals()?',
  a: 'Answer HTML. May use <strong>, <code>, <ul><li>, and an optional ' +
     '<div class="ex-label">Example</div><pre><code>…</code></pre> block. ' +
     'Rendered via innerHTML, so angle brackets in content are entities (&lt; / &gt;).'
}
```

**`extras`** is a *single* topic object (same shape as a `topics` entry) merged
in at runtime as a 13th section: `{ id: 'extras', name, desc, questions: [...] }`.
Its questions are prefixed with a bracketed area tag, e.g. `'[Redis] …'`,
`'[Kafka] …'`, `'[Docker] …'`.

### `leetcode.js` — problems + solutions

**`leetcode`** is an array of 110 problem objects, **pre-sorted by `bucket`**.
The 15 buckets in display order (with current counts):

> Arrays & Hashing (18) · Two Pointers (6) · Sliding Window (7) · Stack (6) ·
> Binary Search (6) · Linked List (11) · Trees (17) · Tries (2) ·
> Heap / Priority Queue (4) · Backtracking (6) · Graphs (8) ·
> Advanced Graphs (3) · Dynamic Programming - 1D (10) ·
> Dynamic Programming - 2D (5) · Greedy (1)

```js
{
  num: 1,                                  // display number 1..110, unique; the join key for the other files
  title: 'Two Sum',
  d: 'easy' | 'medium' | 'hard',
  companies: ['Temu'],                     // OPTIONAL — tags shown on the row (present on ~16 entries)
  bucket: 'Arrays & Hashing',              // one of the 15 groups; consecutive entries share a bucket
  category: 'Array · Hash Map',            // finer per-row tag
  url: 'https://leetcode.com/problems/two-sum/',
  approach: 'One-pass hash map: for each element, check its complement…',
  complexity: 'O(n) time · O(n) space',
  code: `public int[] twoSum(int[] nums, int target) {
  // raw Java — written with real <, >, & (escaped at render time)
  …
}`
}
```

The renderer groups by **consecutive** `bucket` values, so keep entries sorted.
Shared node types (`ListNode`, `TreeNode`, `Node`) are assumed by the
tree/linked-list/graph solutions and documented at the top of the file.

### `descriptions.js` — problem statements

**`leetcodeDescriptions`** maps a LeetCode `num` → an HTML string (2–4
sentences) shown in the expanded panel.

```js
const leetcodeDescriptions = {
  1: 'Given an integer array <code>nums</code> and a <code>target</code>, return the indices…',
  2: 'Given an array <code>prices</code>…',
  // …keyed by num
};
```

### `algorithms.js` — named-algorithm notes

Two objects:

```js
// 1) Explanations + worked example traces, keyed by an algorithm slug
const namedAlgorithms = {
  'kadane': {
    name: "Kadane's Algorithm",
    explanation: 'A linear-time algorithm for the maximum-sum contiguous subarray…',
    example: `nums = [-2, 1, -3, 4, …]   // multi-line trace`
  },
  // 'dutch-national-flag', 'cyclic-sort', 'dijkstra', … (only NAMED algorithms;
  // generic techniques like "DFS" or "two pointers" are intentionally omitted)
};

// 2) Which named algorithm(s) each problem uses, keyed by LeetCode num
const problemAlgorithms = {
  6:  ['bucket-sort'],
  11: ['kadane'],
  46: ['floyd-cycle'],
  // …only problems that use a named algorithm appear here
};
```

The renderer joins `problemAlgorithms[num]` → `namedAlgorithms[key]` to show an
"Algorithm" block in a problem's detail panel.

### `user-overrides.js` — personal solution edits

**`leetcodeUserOverrides`** maps a LeetCode `num` → a replacement `code` string.
When present, it overrides the canonical `code` from `leetcode.js` for that
problem. This file is generated by the floating **"Export edits"** button
(bottom-left of the LeetCode view on the live site): edit a solution in place,
export, replace this file, commit, and redeploy.

```js
const leetcodeUserOverrides = {
  16: `public int[][] merge(int[][] intervals) { … }`,
  18: `public void rotate(int[][] matrix) { … }`,
  30: `public int subarraySum(int[] nums, int k) { … }`,
};
```

### How the data files join

```
leetcode.js  ── num ──┬── descriptions.js   (leetcodeDescriptions[num])
                      ├── algorithms.js      (problemAlgorithms[num] → namedAlgorithms[key])
                      └── user-overrides.js  (leetcodeUserOverrides[num] overrides code)

content.js   topics[] + extras  ──merged at runtime──►  allTopics  (Topics view + chat local index)
```

`num` is the universal join key across the LeetCode files; `id` anchors topic
sections in the Topics view.

## The chat backend (`api/chat.js`)

A single Vercel **Edge** function (`export const config = { runtime: 'edge' }`),
auto-discovered from the `api/` folder — no `vercel.json` needed.

Flow on each `POST /api/chat`:

1. Reject non-POST → **405**.
2. Extract the client IP (`x-forwarded-for` first hop, else `x-real-ip`).
3. Per-IP, per-day **rate limit** (`DAILY_LIMIT = 10`) → **429** if exceeded.
   This counter is per-Edge-instance memory, so it's a soft deterrent only.
4. Require `GROQ_API_KEY` env var → **503** if missing.
5. Parse `{ messages: [{ role, content }, …] }` → **400** if malformed. Keeps
   the last 8 turns, clips each to 2000 chars, prepends the system prompt.
6. Forward to Groq (`POST https://api.groq.com/openai/v1/chat/completions`,
   OpenAI-compatible schema, `model: llama-3.3-70b-versatile`,
   `max_tokens: 350`, `stream: true`) → **502** on upstream failure.
7. **Normalize the SSE stream**: read Groq's
   `data: {"choices":[{"delta":{"content":"…"}}]}` events and re-emit them as
   `data: {"text":"…"}\n\n`, terminated by `data: [DONE]`.

Keeping the response wire-format provider-agnostic means swapping providers only
touches this one file. The chat has historically been wired to Anthropic Claude
Haiku, then Google Gemini, and now Groq (most reliable free tier).

**Required env var:** `GROQ_API_KEY` (free key at https://console.groq.com).
Set it in Vercel → Project → Settings → Environment Variables, then redeploy.

## Local development

The project is dependency-free to *run*; you only need Node for linting.

```bash
# Serve the folder (file:// works in Firefox but Chrome blocks loading the
# data .js files from disk due to cross-file CORS)
npx serve .
# or
python -m http.server
# then open http://localhost:8000
```

### Linting

ESLint (flat config in `eslint.config.mjs`) covers every `.js` file and is aware
of the cross-script globals so the data files don't trip `no-unused-vars`.

```bash
npm install   # one-time, fetches eslint + globals
npm run lint
```

The inline `<script>` in `index.html` isn't linted by ESLint — syntax-check it
with `node --check` after edits. **Convention: run `npm run lint` after any JS
edit and fix all issues before committing.**

## Deployment

- **Vercel project:** `java-interview-prep` (scope `ians-projects-9fd6e881`),
  production alias `java-interview-prep-blush.vercel.app`.
- **Deploys are manual:** from the project root, run

  ```bash
  vercel deploy --prod --yes
  ```

  The Git → Vercel integration is **not** connected, so pushing to GitHub does
  not auto-deploy. To enable auto-deploy, grant the Vercel GitHub app access to
  the repo and connect it in the project's Git settings.
- Always commit and redeploy when there's a content or code change.

## Adding / editing content

**A question:** append a `{ d, q, a }` object to the relevant topic's
`questions` array in `content.js`. The `a` field is HTML (`innerHTML`), so use
`&lt;`/`&gt;` for literal angle brackets; add an example with
`<div class="ex-label">Example</div><pre><code>…</code></pre>`.

**A LeetCode problem:** append an entry to `leetcode.js` **in the right bucket
position** (entries must stay grouped by `bucket`). Write `code` as raw Java —
it's escaped at render time. Optionally add a matching `descriptions.js` entry
and an `algorithms.js` `problemAlgorithms` mapping keyed by the same `num`.

**A topic:** add a topic object to the `topics` array in `content.js`.

See [`ARCHITECTURE.md`](./ARCHITECTURE.md) for fuller examples, and
[`CLAUDE.md`](./CLAUDE.md) for the agent-facing conventions.

## Conventions to preserve

- Keep `content.js`, `leetcode.js`, `descriptions.js`, `algorithms.js`, and
  `user-overrides.js` as **classic scripts** (never `type="module"`).
- Keep `leetcode[]` **pre-sorted by `bucket`** — the section-header grouping
  relies on consecutive entries sharing a bucket.
- Don't regress the click-to-expand guard
  (`if (e.target.closest('.q-answer')) return;`) — it lets users select answer
  text without collapsing the row.
- Preserve the sticky-header anchor offset (`html { scroll-padding-top: 80px }`)
  and the `-webkit-backdrop-filter` on the header (Safari).
- `num` is the join key across all LeetCode data files — keep it consistent.
