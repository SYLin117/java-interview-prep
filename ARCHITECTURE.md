# Architecture

A hand-edited static interview-prep site served from Vercel. Four top-level views — a Java/Spring question bank (**Topics**), a 200-problem **LeetCode** collection, **Garmin Behavioral** question chains, and a **System Design** section — plus a floating chat widget backed by a Vercel Edge function that calls Groq, and a publish-from-the-page editing pipeline for LeetCode solutions. No build step, no bundler, no framework: one HTML file, seven data files, and three Edge functions.

This file explains how the site works. For editing conventions (adding questions, LeetCode entries, code examples), see `CLAUDE.md`.

## At a glance

- **Static HTML/CSS/JS.** Open `index.html` and everything is right there — no compilation.
- **Content is data, not markup.** Every view renders from a plain-JS data file (`content.js`, `leetcode.js`, `behavioral.js`, `systemdesign.js`, …). Adding content never touches HTML.
- **Four views, one page.** Header buttons toggle between the views via the `[hidden]` attribute; URL-hash routing keeps each view linkable.
- **Single inline script** in `index.html` orchestrates everything (render, view toggle, filters, search, chat, editing). No modules, no `defer` on data scripts — order matters.
- **Three serverless functions** in `api/`: `chat.js` proxies chat to Groq (rate limiting + SSE normalization), `leetcode.js` proxies official LeetCode problem statements, and `overrides.js` stores solution edits published from the page (Upstash Redis, master-key gated). All three are optional — the page degrades to fully-static behavior without them.
- **Vercel hosting** with manual `vercel deploy --prod --yes`. Auto-deploy via the GitHub integration isn't wired up.

All browser-side JS files are loaded as classic (non-module) scripts in this order: `content.js`, `leetcode.js`, `descriptions.js`, `algorithms.js`, `user-overrides.js`, `behavioral.js`, `systemdesign.js`, then the inline script. Each declares top-level `const`s — JavaScript's classic-script global lexical scope shares them across all `<script>` tags on the page, so the inline script reads them directly. Don't convert any of them to `type="module"`; module scope would break every cross-file reference.

## Page lifecycle

When the browser loads the page:

1. **HTML parses top-down.** The head loads Google Fonts (JetBrains Mono) and highlight.js (JS with `defer`, so it runs after the document parses) with the atom-one-dark theme.
2. **Body parses.** Sticky header (brand, four-button view toggle, search box, stats), `<div id="topics-view">` (visible), the three other view wrappers (`hidden`), footer, the floating LeetCode-edit button row, and the chat widget skeleton.
3. **The seven data scripts run**, defining the shared globals.
4. **Inline script runs** (synchronously), top to bottom:
   - Merge `topics` + `extras` into `allTopics`; overwrite the header's topic/question counts
   - Build the topic filter dropdown and all topic sections inside `#content`
   - Attach click handlers to `.q-row.q-data` (expand/collapse)
   - Run highlight.js on topic-answer code blocks (or queue for the `load` event if hljs isn't ready yet)
   - Build all LeetCode rows (with bucket header rows) inside `#leetcode-table`
   - Fire a one-time `fetch('/api/overrides')` to layer published edits onto the table
   - Render the Behavioral and System Design views and their filters
   - Wire view-toggle buttons + URL-hash routing
   - Wire the view-aware search input
   - Wire the entire chat widget (open/close/send/cancel/resize, plus the local Q&A index)
5. **User interacts.** Click handlers and event listeners take over.

Each section of the inline script has a `// ─── Section name ───` header.

One hoisting subtlety: `escapeHtml()` is defined near the bottom of the script (chat-widget section) but called by the LeetCode renderer far above it. It works because `function` declarations hoist — don't turn it into a `const`.

## Four-view architecture

The header has a segmented control (`.view-toggle`) with four buttons: **Topics**, **LeetCode 200**, **Garmin Behavioral**, **System Design**. Exactly one view is in the layout at a time via the standard HTML `hidden` attribute. `setView(view, opts)` is data-driven from three maps (`VIEW_EL`, `VIEW_HASH`, `VIEW_PLACEHOLDER`): it toggles visibility, updates active button state (visually + ARIA), swaps the search placeholder, syncs the URL hash via `history.replaceState`, clears the search input (dispatching `input` so filtered rows reappear), and scrolls to top.

| URL hash | View shown |
|---|---|
| (none) | Topics |
| `#core-java`, `#multithreading`, … (topic ids) | Topics, with that topic selected in the filter dropdown |
| `#leetcode` or `#lc` | LeetCode |
| `#behavioral` | Garmin Behavioral |
| `#systemdesign` or `#sd` | System Design |

A `hashchange` listener handles direct links to any view. A topic-anchor hash does double duty: it switches back to the Topics view *and* pre-selects that topic in the dropdown — the chat widget's "See *Topic* →" links rely on this.

## Topics view

For each topic in `allTopics`, the inline script builds a `<section class="section topic-section" id="...">` with a header (number, title, description) and a `<div class="q-table">` of one `.q-row.q-data` per question. The last section renders as "Bonus Section" instead of a number.

Questions are **sorted by difficulty** at render time (easy → medium → hard) using a stable sort on a `{ easy: 0, medium: 1, hard: 2 }` rank map, so the displayed numbers within each topic always run easy first.

Each row's `data-q` and `data-a` attributes hold the lowercased question text and the lowercased plain-text of the answer (HTML stripped), used by search.

A **topic dropdown** in the sticky filter bar narrows the view to one topic (this replaced an earlier side-nav + topic-card design). The dropdown and the search term compose: the dropdown hides non-matching sections, search then filters rows within visible sections and hides sections with zero hits.

### Click-to-expand

Clicking a `.q-row.q-data` toggles `.expanded`, revealing the `.q-answer` child. Clicks that originate inside `.q-answer` are deliberately **ignored** so users can select and copy answer text without collapsing the row:

```js
row.addEventListener('click', (e) => {
  if (e.target.closest('.q-answer')) return;   // let users select detail text
  row.classList.toggle('expanded');
});
```

Don't regress this — it's a key UX detail, applied identically in the Behavioral and System Design views.

## LeetCode view

### Render pipeline

Iterates over `leetcode[]` once, inserting a styled bucket-header row (with a per-bucket problem count) whenever the `bucket` field changes — which is why the array must stay pre-sorted by bucket. Each `.lc-row.lc-data` has 6 columns: official LeetCode number (`lc`), difficulty pill, title (plus company pills like Garmin/Temu from the `companies` field), category, "LeetCode ↗" link, and expand toggle. Some columns collapse at smaller widths via media queries.

The stable internal `num` (not in array order) keys everything cross-file: `user-overrides.js`, `descriptions.js`, and `algorithms.js`.

Unlike topic answers (pre-escaped HTML), LeetCode `code`, `title`, `approach`, and `complexity` are stored as plain strings and run through `escapeHtml()` at render time — so Java generics can be written naturally (`Map<String, Integer>`) in `leetcode.js` template literals.

### The expanded detail panel

Expanding a row assembles up to five blocks:

1. **Problem** — the paraphrased statement from `descriptions.js`, upgraded in place to the **official LeetCode statement** on first expand via `/api/leetcode?slug=…`. Results are cached in an in-memory map + `localStorage` (`lc_desc_<slug>`), so each problem is fetched at most once per device. Any failure keeps the paraphrase and adds a warning badge; the row retries on a later expand.
2. **Approach** — the one-liner from `leetcode.js`.
3. **Algorithm** (only for mapped problems) — the named-algorithm explainer(s) from `algorithms.js`, each with name, explanation, and a worked example trace.
4. **Complexity**.
5. **Java** — the solution code block, which is editable (next section).

The fetch also cross-checks identity: if the slug resolves to a *different* official problem number than the entry claims, the row gets a "⚠ wrong slug?" badge and the description gets a warning banner. A **"Verify official statements"** button in the filter bar sweeps every problem through this check with six concurrent workers and summarizes failures/mismatches on the button and in the console.

### Lazy syntax highlighting

Topic answers highlight eagerly at load. LeetCode highlights **only when a row is first expanded** — 200 Java blocks would be wasteful work for code the user might never open. Solution blocks are highlighted through `initEditableCode()`; read-only algorithm examples go through a `pre code:not(.hljs):not([data-lc-num])` pass (the `:not(.hljs)` guard makes it once-per-block).

### Editable solutions and the override layering

Every solution block is `contenteditable`. What a visitor sees for problem `num` resolves through four layers:

1. **localStorage draft** (`lc_code_<num>`) — your in-progress edit, this device only
2. **published override** — fetched from `GET /api/overrides`, served to every visitor instantly
3. **`user-overrides.js`** — committed personal edits (needs commit + redeploy)
4. **canonical `leetcode.js`** code

`lcBaseCode(num)` resolves layers 2–4; drafts overlay at runtime. Edits auto-save to the draft with a 400 ms debounce; if an edit brings the text back to exactly the live base, the draft is deleted instead (so hand-undo leaves no stale draft). Typing tears up highlight.js's spans, so blur rebuilds the block from `textContent` and re-highlights. On init, highlighting runs *before* `contenteditable` is set because the highlighter's DOM rewrite would strip the attribute.

Four floating buttons (bottom-left, LeetCode view only):

- **📥 Export N edits** — downloads a merged `user-overrides.js` (committed + published + drafts, drafts winning) to commit to git. Code is wrapped in template literals with backslash, backtick, and `${` escaped (backslash first — order matters).
- **☁ Publish N edits** — PUTs each draft to `/api/overrides` sequentially, then clears the drafts. Shown only while unlocked.
- **🗑 Clear N edits** — confirm, then discard every local draft and revert rows to their base.
- **🔑 / 🔓** — prompts for the master key, verifies it against the server (`GET` reports `canEdit`), stores it in `localStorage` (`lc_master_key`), and flips to 🔓 while unlocked. A stored key the server no longer accepts (rotated on Vercel) is forgotten automatically.

The per-row reset button is dual-mode: with a draft it reads **"Reset to original"** (discard the draft); with no draft, a published override present, and the key unlocked it becomes **"Remove published edit"** (confirm → `PUT { code: null }`).

## Garmin Behavioral view

Each chain in `behavioral[]` renders as a `.behavioral-section`: the main question is the section title, row one is the suggested STAR answer (marked ★), and the remaining rows are the likely follow-ups — the layout mirrors how an interview actually unfolds. A category dropdown filters chains; search matches against a flattened `data-search` string containing the main question, answer, and every follow-up Q&A. Answers are trusted HTML; `[Personalize: …]` notes mark spots for the owner to drop in a real metric or detail.

## System Design view

Two sub-tabs (`.sd-subtab`, state variable `sdSubtab`):

- **Concepts** — one topic-style section per theme in `systemDesignThemes`, rows sorted easy → hard, with a theme dropdown (shown only in this mode).
- **Case Studies** — one `.sd-case` card per entry in `systemDesignCases`, expanding from its header into labelled `.sd-block`s: Problem, Requirements, Capacity Estimation, Core Components, Deep Dive, Request Flow (plain text in a `<pre class="sd-flow">` — everything else is HTML), and Trade-offs.

`applySystemDesignFilters()` targets whichever sub-tab is active; switching sub-tabs re-applies filters and scrolls to top.

## Search

One search input serves all four views — the `input` handler routes the term to whichever view is visible, where it composes (AND) with that view's dropdown filters:

| Active view | What's searched | What gets hidden |
|---|---|---|
| Topics | `data-q` + `data-a` + topic name | Non-matching rows; whole sections with zero hits |
| LeetCode | title + category + bucket + approach (`data-q`) | Non-matching rows; bucket headers whose group is empty |
| Behavioral | whole chain (`data-search`) | Non-matching chain sections |
| System Design | active sub-tab (rows or whole case cards) | Rows/sections or cards |

Switching views via `setView` clears the input (dispatching `input` so filtered rows reappear).

## Chat widget

A floating 💬 button (bottom-right) opens a panel: title bar, scrollable message list, textarea + Send form, and a resize handle (desktop only).

### Local Q&A index

Before calling the LLM, the widget tries to answer locally with a token-overlap index built at boot from every topic question. Tokenization lowercases, splits on non-alphanumerics, drops tokens under 3 chars and ~90 stopwords; each question stores a `Set` of its tokens. A query short-circuits to the on-site answer only if **≥60% of its significant tokens overlap AND ≥2 tokens match absolutely**. A hit renders the canonical answer with a "📚 From your notes" tag and a deep link to the topic — no network call, no tokens spent. A plain-text snapshot of the answer goes into the history so follow-ups have context.

### Streaming flow

On a miss, the widget POSTs the conversation history to `/api/chat` (the function keeps only the last 8 turns, clipped to 2,000 chars each). The response is a stream of `data: {"text": "chunk"}\n\n` SSE events; the widget accumulates chunks into the bubble as plain text and auto-scrolls, then converts the finished text with `renderChatMd()`. An `AbortController` cancels the in-flight fetch when the panel closes or a new message is sent.

### Markdown rendering

`renderChatMd()` handles a deliberately tiny subset: escape all HTML first, stash fenced code blocks behind placeholders, convert inline backticks and newlines, restore the blocks. No full Markdown library — keeps the page weight tiny, and the system prompt instructs the model toward concise, code-y output anyway.

### Resize (desktop only)

CSS hides the handle unless `(pointer: fine)` and the viewport is ≥768px. Pointer capture keeps the drag attached; the panel is anchored bottom-right, so dragging up/left grows it. Size is clamped (min 280×360, max 720 wide × viewport-height − 80) and persisted to `localStorage['chatPanelSize']`.

## Backend: the three Edge functions

### api/chat.js

1. **Method check** — reject anything but POST with 405.
2. **Extract client IP** from `x-forwarded-for` (first hop) or `x-real-ip`.
3. **Rate limit** — per-IP per-day counter, `DAILY_LIMIT = 10`, 429 when over. Per-Edge-instance memory, so it's a soft deterrent only.
4. **API key check** — 503 with a clear message if `GROQ_API_KEY` is missing.
5. **Parse + validate body** — `{ messages: [{ role, content }, ...] }`.
6. **Build the Groq request** — system prompt first, then the last **8** turns, each clipped to 2,000 chars. OpenAI chat-completion schema; model `llama-3.3-70b-versatile`, `max_tokens: 350`, `stream: true`.
7. **Handle upstream errors** — non-2xx surfaces as a 502 with the upstream message truncated.
8. **Transform the SSE stream** — parse Groq's `choices[0].delta.content` chunks and re-emit as `data: {"text": "chunk"}\n\n`. The reader loop buffers partial lines (Edge fetch can split SSE events anywhere).

The wire format is the point: the client never learns which provider is upstream, so swapping providers only ever touches this file.

### api/overrides.js

- **`GET`** — public read, always `cache-control: no-store`. Returns `{ enabled, canEdit, overrides }`; `enabled: false` (not an error) when any env var is missing, `canEdit` reports whether the caller's bearer key is accepted (used to verify a typed key).
- **`PUT`** — requires `Authorization: Bearer <master key>`; body `{ num, code }` saves, `{ num, code: null }` deletes. Keys are compared via SHA-256 digests (a plain `===` on secrets is timing-observable in principle). Validation: `num` a positive integer ≤ 100,000, `code` ≤ 50 KB. Failed key attempts are soft-limited at 30/IP/day (same per-instance caveat as chat).

Storage is one Upstash Redis hash `lc:overrides` (field = problem `num`, value = Java source), reached over the REST API with commands POSTed as JSON arrays — keeping code payloads out of URL paths.

### api/leetcode.js

Exists because the browser can't call `leetcode.com/graphql` (CORS) and statements live behind GraphQL, not page HTML. `GET /api/leetcode?slug=two-sum` → `{ id, title, difficulty, content }`. The slug is validated against `^[a-z0-9]+(-[a-z0-9]+)*$`; the GraphQL call sends a realistic User-Agent and Referer (LeetCode 403s naked requests). Success responses carry `s-maxage=604800, stale-while-revalidate=86400` — each problem hits LeetCode at most once per cache window across all visitors. Needs no env var.

## Provider history

The chat backend went through three providers during development:

1. **Anthropic Claude Haiku 4.5** — best quality, paid (no free tier without credits).
2. **Google Gemini 2.0 Flash** — free tier in theory, but returned 429 "project quota exhausted" on a fresh key.
3. **Groq Llama 3.3 70B Versatile** — current. Reliable free tier (14,400 req/day, no credit card), very fast inference.

Each switch only required rewriting `api/chat.js` — the client wire format stayed the same throughout. To swap again: update the upstream URL, auth header, request body shape, and SSE delta-extraction.

## Conventions baked in (don't regress)

- **Sticky-header anchor offset** — `html { scroll-padding-top: 80px }` makes anchor jumps land below the header.
- **Click-on-answer-doesn't-collapse** — the guard `if (e.target.closest('.q-answer')) return;` is essential UX (same idea for `.lc-detail` in the LeetCode view).
- **`overflow-wrap: anywhere`** on inline `<code>` — long identifiers must wrap on mobile.
- **`-webkit-backdrop-filter`** alongside `backdrop-filter` on the sticky header — Safari needs it.
- **`escapeHtml()` stays a hoisted `function` declaration** — the LeetCode renderer above it depends on hoisting.
- **All data files stay classic scripts** (no `type="module"`) — they expose globals the inline script reads.
- **`leetcode.js` stays pre-sorted by bucket** — the renderer groups consecutive entries.
- **Never renumber existing `num` values** — they key `user-overrides.js`, `descriptions.js`, `algorithms.js`, and the published overrides in Redis.

## Local preview

Opening `index.html` directly via `file://` works in Firefox but Chrome blocks the data files (cross-file CORS on local files). Use any static server from this folder:

```bash
npx serve .
# or
python -m http.server
```

The `/api/*` features need a Vercel deployment; the page degrades gracefully without them.
